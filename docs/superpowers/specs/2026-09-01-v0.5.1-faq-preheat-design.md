# v0.5.1 FAQ 极速预热设计

## 1. 目标

在员工实际提问前，系统从最新版制度资料中自动挑选最可能成为高频问答的高价值切片，生成并直接启用标准答案。员工第一次提出命中问题时即可本地直发，不等待 15 天内累计 3 次。

本设计以速度为优先：员工命中预热 FAQ 时只执行本地 SQLite 检索、意图匹配、资料版本校验和答案清洗，不调用 DeepSeek。

## 2. 已确认决策

- 预置候选可在第一次命中时直接回复。
- 候选由规则筛选，不使用向量数据库或 Embedding API。
- 标准问题、同义问法和标准答案由 DeepSeek 在预热阶段自动生成。
- 每个知识空间最多预热 10 个候选。
- 每个空间使用 2 个并行生成任务。
- 预热在同步成功后后台执行，不占用员工消息处理线程。
- 已有 v0.5.0 的资料版本、个人标识过滤、答案清洗和权限范围隔离继续生效。

## 3. 前置条件

本功能建立在已发布的 v0.5.0 高频问答索引之上。v0.5.0 的以下发布阻断项必须先关闭：

1. 本地索引删除文件后能原子清理旧文档并递增版本；
2. FAQ 报表使用只读 SQLite 连接；
3. README、CHANGELOG 与实际版本、隐私声明一致；
4. 资料版本变化时旧 FAQ 状态和失效指标一致。

预热功能不与未完成的 v0.5.0 修复混合部署。

## 4. 候选筛选

### 4.1 候选输入

每个完整成功同步的知识空间，以当前 `knowledge_revision` 下的 `chunks` 为输入。纯目录、短标题、空正文、来源不明、包含个人标识或不能通过现有安全检查的切片不参与候选。

### 4.2 本地评分

候选评分只使用本地规则：

| 信号 | 分值 | 说明 |
|---|---:|---|
| 标题/章节含流程、审批、报销、供应商、准入、认证、表单、时限、职责 | +3 | 高频制度问答信号 |
| 正文含有序步骤、条件、责任部门、时限、表单编号或审批节点 | +2 | 可形成可执行答案 |
| 切片长度在 300–1,500 个字符 | +1 | 信息完整且不冗长 |
| 标题含制度或程序编号 | +1 | 资料稳定性更高 |
| 目录、附件索引、模板说明或正文过短 | 直接排除 | 不生成固定答案 |

候选按分数、资料编号和 `chunk.id` 稳定排序。同一 `source_id` 最多保留 1 个候选，避免一个长流程占满名额。每空间只保留前 10 个。

### 4.3 候选签名

候选签名由空间 ID、`chunk.id`、`source_id`、当前内容哈希和 `knowledge_revision` 计算。签名未变化的候选不得重复调用 DeepSeek。

## 5. 预热生成

### 5.1 后台任务

完整成功同步并原子提交文档后，在 `faq_preheat_jobs` 中写入 `(space_id, knowledge_revision)` 作业。新建后台 worker 轮询待处理作业；同一空间同一版本只有一个待处理或运行中的作业。

worker 以 2 个并行任务处理该空间候选。预热作业与 Webhook、飞书长连接、同步主流程分离。同步完成即可返回，不等待 DeepSeek 生成结束。

### 5.2 DeepSeek 输出契约

每个候选使用结构化 JSON 生成：

```json
{
  "canonical_question": "标准问题",
  "aliases": ["同义问法一", "同义问法二"],
  "answer": "仅依据候选资料的简洁答案",
  "evidence_sufficient": true
}
```

要求：

- `aliases` 最多 5 条，必须是问题表达，不得包含员工身份；
- `answer` 只能依据候选切片，不能补造制度；
- 候选、问题或答案出现个人标识、来源、URL、IP、密钥或不安全内容时拒绝；
- `evidence_sufficient=false`、JSON 无效或模型失败时将该候选标为失败，不重试同一轮作业；
- 单个候选失败不影响同空间其他候选。

## 6. 数据模型

### 6.1 `faq_preheat_jobs`

| 字段 | 类型 | 说明 |
|---|---|---|
| id | TEXT | UUID 主键 |
| space_id | TEXT | 知识空间 ID；本地资料使用固定 local scope |
| knowledge_revision | INTEGER | 入队时资料版本 |
| state | TEXT | `queued`、`running`、`completed`、`failed` |
| created_at | REAL | 入队时间 |
| started_at | REAL | 开始时间 |
| finished_at | REAL | 完成时间 |
| candidate_count | INTEGER | 本轮候选数 |
| generated_count | INTEGER | 成功生成数 |
| failed_count | INTEGER | 候选失败数 |

`(space_id, knowledge_revision)` 必须唯一。作业开始和完成均以版本栅栏校验当前资料版本；旧版本作业直接标记 `completed`，不写 FAQ。

### 6.2 `faq_preheat_candidates`

| 字段 | 类型 | 说明 |
|---|---|---|
| candidate_signature | TEXT | 候选唯一签名 |
| space_id | TEXT | 所属空间 |
| knowledge_revision | INTEGER | 候选资料版本 |
| chunk_id | TEXT | 来源切片 |
| source_id | TEXT | 来源文档 |
| score | INTEGER | 本地筛选分数 |
| state | TEXT | `selected`、`generated`、`rejected`、`failed` |
| faq_id | TEXT | 成功后关联的 FAQ |
| created_at | REAL | 创建时间 |
| updated_at | REAL | 最近状态时间 |

### 6.3 `faq_entries` 扩展

新增：

| 字段 | 类型 | 说明 |
|---|---|---|
| origin | TEXT | `observed` 或 `preheated` |
| preheat_candidate_signature | TEXT | 预热候选签名；观察晋级为空 |

预热 FAQ 使用现有 `scope_key`、`intent_key`、`source_ids_json`、`knowledge_revision`、`state` 和安全答案字段，员工直接命中路径不区分来源类型。

## 7. 命中与刷新

1. 预热生成成功后，按标准问题与同义问法构造既有 `FaqObservation`，写入 `origin=preheated` 的 `enabled` FAQ。
2. 员工第一次提问时，现有 `FaqService` 使用意图键、文本相似度、来源重叠、权限范围和版本检查命中，直接发送答案。
3. 当前资料版本变化时，v0.5.0 的原子版本提交将旧 FAQ 标记为 `stale`；旧预热作业也不能写入。
4. 新版本空间的后台预热成功后，覆盖同一意图的旧预热 FAQ；未再入选的候选保持 `stale`，不再直发。
5. 未预热的问题仍按 v0.5.0 的真实问答 15 天/3 次规则处理。

## 8. 速度与成本

- 员工命中预热 FAQ：本地 SQLite 查询，不调用 DeepSeek。
- 同步主流程：不等待预热 worker，不增加同步完成延迟。
- 预热调用上限：每空间最多 10 次候选生成，每次最多 2 个并行任务。
- 未变化候选由签名跳过，避免重复费用。
- 预热指标单独统计 `preheat_calls`、`preheat_generated`、`preheat_failed`、`preheat_direct_hits`，不混淆普通 FAQ 命中率。

## 9. 安全与隐私

速度优先不移除以下本地低成本硬护栏：

- 资料版本栅栏；
- 权限范围隔离；
- 个人标识问题和答案拒绝进入 FAQ；
- 来源、URL、IP、密钥和危险输出拦截；
- DeepSeek 失败不启用候选；
- 预热 worker 不记录员工问题或身份。

这些检查不在员工命中路径调用额外模型，不影响直发速度。

## 10. 失败处理

- worker 崩溃：运行中作业按租约超时回到 `queued`，最多重试 1 次；
- 资料版本变化：旧作业停止写入，等待新版本作业；
- 候选生成失败：记录候选失败，继续处理其余候选；
- 预热表或任务队列不可用：同步和普通 RAG 保持可用，预热跳过并记录脱敏错误；
- 命中验证不充分：回退普通 RAG，不发送预热答案。

## 11. 配置

```dotenv
RAG_FAQ_PREHEAT_ENABLED=true
RAG_FAQ_PREHEAT_MAX_PER_SPACE=10
RAG_FAQ_PREHEAT_WORKERS=2
RAG_FAQ_PREHEAT_MAX_RETRIES=1
```

校验范围：候选数 1–50，并行数 1–8，重试次数 0–2。关闭开关后不入队、不生成、不影响已存在的普通 FAQ。

## 12. 测试与验收

必须覆盖：

1. 同一文档只选 1 个候选，空间候选不超过 10 个；
2. 评分稳定，同分候选顺序稳定；
3. 预热问题与“供应商开发流程”“新供应商怎么导入”等同义问法可首次直接命中；
4. 不同来源、不同空间或版本不共用预热答案；
5. 候选签名不变不重复调用 DeepSeek；
6. 文档更新后旧预热 FAQ 失效，旧作业不能写入，新作业生成后恢复直发；
7. 候选模型失败、证据不足、不安全输出和个人标识均不启用；
8. 2 个并行 worker 不生成重复 `(space_id, revision)` 作业；
9. 同步、Webhook、长连接和普通 RAG 在预热 worker 失败时仍可用；
10. 预热直发不调用 DeepSeek，且仍受版本、权限、限流和输出清洗保护；
11. SQLite 迁移兼容 v0.5.0 已有 FAQ 数据；
12. 完整测试、编译、Compose 配置、敏感信息扫描和系统服务部署验收通过。

## 13. 发布与回滚

发布版本为 v0.5.1。部署时同时更新 `rag`、`rag-events` 和预热 worker 服务；先备份 SQLite，再执行三个空间完整同步，确认预热作业入队、每空间候选上限、首次命中直发和资料更新刷新。

回滚时设 `RAG_FAQ_PREHEAT_ENABLED=false`，停止预热 worker。已生成的 `preheated` FAQ 标记为 `stale`，普通 v0.5.0 FAQ 与 RAG 保持可用。
