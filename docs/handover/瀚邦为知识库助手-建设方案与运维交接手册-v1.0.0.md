
飞书中为三个部门分别建立知识空间，员工默认可以读取全部文档。当前未做部门级数据隔离。

### 2.2 为什么没有使用飞书内置知识问答应用

飞书内置应用使用方便，但需要额外付费。公司已经具备 Ubuntu 服务器和 DeepSeek API 额度，因此最终采用自建方案：

1. 自行开发轻量 RAG 后端。
2. 使用公司已购买的 DeepSeek API。
3. 将服务部署到公司 Ubuntu 服务器。
4. 通过飞书企业自建机器人向员工提供问答。

这个方案的主要优点是成本可控、数据流程可解释、知识库更新可自动化，并且后续可以继续扩展权限过滤和检索能力。

### 2.3 为什么新建机器人

原有机器人 Mira 依赖 Kimi 账号，不适合作为公司全员、统一使用 DeepSeek 的内部知识库入口。最终保留 Mira，不再复用其应用身份，另外创建企业自建应用“瀚邦为知识库助手”。

新应用只绑定本项目的 Ubuntu 服务和 DeepSeek API。所有员工都可以搜索并使用该机器人，外部群和外部联系人被禁用。

## 4. 总体架构

### 4.1 在线问答链路

```text
员工飞书消息
  -> 飞书企业自建应用
  -> 长连接事件 im.message.receive_v1
  -> rag-events 容器
  -> SQLite 关键词召回 Top 6
  -> DeepSeek 基于召回原文生成回答
  -> 程序清理来源区块和引用编号
  -> 飞书机器人回复员工
```

### 4.2 知识同步链路

```text
systemd 每小时定时器
  -> 飞书 Wiki 递归遍历
  -> 下载 DOCX、PDF 等附件
  -> 本地解析或中文 OCR
  -> 本地结构切分为原子段落
  -> DeepSeek 只规划语义分组并生成标题、关键词、摘要
  -> 程序用原文重新组合正式切片
  -> 写入 SQLite
```

### 4.3 关键边界

- 飞书负责员工身份、机器人入口和知识文档存储。
- Ubuntu 服务器负责同步、解析、OCR、索引、检索和消息处理。
- DeepSeek 负责语义分组元数据和最终回答生成。
- SQLite 保存文档、切片和已处理消息 ID。
- 当前没有向量数据库，也没有额外的 Embedding API 费用。

## 7. 文档接入与同步逻辑

### 7.1 支持格式

系统支持 PDF、DOCX、TXT 和 Markdown。扫描型 PDF 会使用 Tesseract 中文 OCR。

旧版 `.doc` 和 `.wps` 建议先转换为 `.docx`，避免解析效果不稳定。

### 7.2 递归同步

最初同步逻辑只处理知识空间根目录，导致目录下 PDF 附件没有进入索引，员工询问财务报销时出现“资料不足”。后续已经改为递归遍历子目录，并通过飞书云盘接口下载附件。

同步时执行以下步骤：

1. 从三个 Space ID 开始递归列出节点。
2. 对 DOCX 读取原始正文。
3. 对支持的附件下载到临时目录。
4. 在服务器本地完成解析和 OCR。
5. 计算内容、模型和切片策略的联合校验和。
6. 文档未变化时跳过，避免重复 OCR 和重复消耗模型额度。
7. 文档变化时重新切片并更新 SQLite。

### 7.3 暂缓纳入的资料

交付过程中发现以下文档存在业务一致性问题，因此没有作为正式知识依据继续扩大使用：

- 供应商 WPS 文档中存在 B1/B0 版本或等级表述不一致。
- 采购协议代码存在不一致，需要业务部门确认正式版本。

接收人不要仅根据文件名直接放入知识库，应先由业务负责人确认有效版本。

## 8. RAG 实现说明

### 8.1 混合切片方案

系统采用“本地结构切分 + DeepSeek 语义规划”的混合方案：

1. 程序按段落和页面把文档拆成稳定编号的原子单元。
2. 超长段落按约 600 字继续切分。
3. 每批最多约 12000 字发送给 DeepSeek。
4. DeepSeek 只返回段落编号分组、标题、关键词和摘要。
5. 程序严格校验编号不能遗漏、重复、乱序或跨越不连续段落。
6. 正式切片正文必须由原文重组，模型不能改写制度正文。
7. 单个正式切片目标上限为 900 字。

这样做可以改善制度文档的语义完整性，同时避免模型生成的文字替代原始制度。

### 8.2 DeepSeek 调用规则

DeepSeek 有两类调用：

- 索引阶段：按批次发送文档正文，返回 JSON 语义分组和检索元数据。
- 问答阶段：只发送用户问题和命中的 Top 6 原文切片，生成最终回答。

语义切片请求显式关闭思考模式，避免思考内容占满输出额度而正文为空。若 DeepSeek 分组失败、JSON 不合法或编号校验失败，系统自动回退本地切片。

### 8.3 检索策略

当前使用 SQLite 本地轻量关键词检索，适合现阶段三部门制度文档规模：

| 命中位置 | 权重 |
|---|---|
| 文档标题 | 3.0 |
| 原始正文 | 1.0 |
| DeepSeek 标题、关键词、摘要 | 0.75 |

中文查询会同时生成完整词和连续双字词。结果按得分排序，默认召回 6 个切片。

当前没有向量数据库。未来文档量明显增加，或同义表达召回率不足时，可以增加 Embedding 和向量检索，但需要重新评估成本、权限过滤和数据外发范围。

### 8.4 回答约束

系统提示词要求 DeepSeek：

- 只能依据召回资料回答。
- 不得补造制度、金额、日期或审批人。
- 资料不足时明确说明“现有资料不足”。
- 不输出资料编号、引用编号或来源列表。

程序还会二次清理“来源”区块和 `[数字]` 引用标记。内部仍保留引用对象，供后台验收使用，但不会发送给员工。

### 8.5 消息去重

飞书可能重复投递同一事件。系统在 SQLite 的 `processed_messages` 表中登记消息 ID：

- 第一次收到时登记并处理。
- 重复消息直接忽略。
- 处理失败时释放登记，允许飞书后续重试。
- 默认保留 7 天后清理。

### 9.3 两个容器

### 9.4 更新部署


### 11.2 SQLite 备份

建议在每次重大升级前使用 SQLite 在线备份接口，而不是运行中直接复制文件：

```bash
cd /opt/data-assistant/feishu-rag
sudo docker compose exec -T rag python -c 'import sqlite3,time; s=sqlite3.connect("/app/data/rag.sqlite3"); d=sqlite3.connect(f"/app/data/rag-backup-{int(time.time())}.sqlite3"); s.backup(d); d.close(); s.close()'
```

### 11.3 回滚原则

1. 停止定时同步，防止回滚期间修改索引。
2. 保留当前数据库，不要直接覆盖。
3. 切回已知正常 Git 提交或部署包。
4. 同时重建 `rag` 和 `rag-events`。
5. 必要时恢复数据库备份。
6. 验证健康检查、监听进程和三类固定问题。
7. 恢复定时同步。

禁止使用 `docker compose down -v`，该命令可能删除数据卷。当前数据使用绑定目录，也不应把清理命令当作常规重启手段。

## 12. 故障记录与处理经验

### 12.1 财务问题返回“资料不足”

根因：旧同步逻辑只处理知识空间根节点，没有递归读取目录中的 PDF 附件。

处理：增加递归遍历、云盘附件下载、本地 PDF 解析和中文 OCR，并清理目录占位索引。

### 12.2 同一个问题回复两次

根因：飞书事件可能重复投递，且早期缺少跨进程持久化去重。

处理：增加 SQLite `processed_messages` 表，按消息 ID 抢占处理权；同时确保生产环境只有一个长连接监听进程。

### 12.3 员工仍看到“来源”

根因：`rag` 已更新到新代码，但 `rag-events` 仍使用旧的 Python 3.11 镜像。员工消息实际由旧容器处理，旧逻辑会自动拼接来源。

处理：重建 `rag-events`，确认其使用 Python 3.14.7 和 v0.2.3 源码。以后每次部署必须同时重建两个服务。

### 12.4 长文没有使用 DeepSeek 语义切片

根因：DeepSeek V4 Flash 在 JSON 规划请求中进入思考模式，正文 `content` 为空，程序因此回退本地切片；旧缓存又阻止长文重新计算。

处理：语义切片 JSON 请求显式关闭思考模式，将策略版本提升到 `hybrid-v2`，强制已有文档重新计算。

## 15. 已知限制与后续建议

### 15.1 当前限制

- 全员可以读取全部知识文档，没有按部门或用户过滤检索结果。
- 使用关键词检索，没有向量语义检索。
- SQLite 适合当前规模，不适合大规模高并发和多实例写入。
- 语义切片会把完整文档分批发送给 DeepSeek。
- 机器人只处理文本消息，不处理图片、语音或表格交互。

### 15.2 后续建议

1. 建立正式的制度文档发布和作废流程，减少版本冲突。
2. 为服务器、DeepSeek 和飞书凭据设置固定轮换周期。
3. 增加同步失败、容器退出和 API 额度异常告警。
4. 文档量增加后评估混合检索，包括关键词、Embedding 和重排序。
5. 如果未来收紧飞书知识权限，RAG 必须增加按员工身份过滤结果，不能只依赖飞书页面权限。
6. 将本地 `main` 推送到 GitHub 默认分支，并建立发布 Tag 和变更审批流程。
